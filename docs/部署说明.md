# CloudCLI 部署说明（Windows / 局域网 HTTPS + 2FA）

本文档对应 fork 仓库 `https://github.com/linchengming/claudecodeui`（在上游基础上增加了 HTTPS、设备证书验证、登录限流、可选 TOTP 两步验证）。

> 文中 `<新机IP>` 请替换为新电脑的局域网 IP，例如 `192.168.1.50`。
> PowerShell 默认禁止运行 `.ps1`，所以下文统一使用 `npm.cmd` / `npx.cmd`。

## 3. 配置 `.env`

在项目根目录（和 `package.json` 同级）新建 `.env`。它已被 `.gitignore` 忽略，**不要提交**。

```ini
SERVER_PORT=33001
# 只监听本机某个网卡就填该 IP；监听所有网卡填 0.0.0.0
HOST=<新机IP>

# HTTPS 证书，生成方法见第 4 节。两行都删掉则退回 HTTP
SSL_KEY_FILE=C:\Users\<用户名>\.cloudcli\certs\server.key
SSL_CERT_FILE=C:\Users\<用户名>\.cloudcli\certs\server.crt

# 设备证书验证（双向 TLS），生成方法见 4.4。删掉这一行就退回普通单向 HTTPS
SSL_CLIENT_CA_FILE=D:\CommonProject\claudecodeui\client-certs\ca.crt

# TOTP 两步验证，生成方法见第 5 节。删掉这一行就关闭 2FA
TOTP_SECRET=<Base32 密钥>

# 项目浏览的根目录，默认是用户主目录
WORKSPACES_ROOT=D:\UnityProject

# 上下文窗口
CONTEXT_WINDOW=160000
VITE_CONTEXT_WINDOW=160000

# 可选：禁止 Claude Code 发送遥测等非必要流量
# CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
```

注意：

- `.env` 格式是简单的 `KEY=VALUE`，不要加引号。已存在的系统环境变量优先生效。
- `VITE_CONTEXT_WINDOW` 在**构建时**写入前端，修改后需要重新 `npm.cmd run build`。
- **绝对不要设置 `VITE_IS_PLATFORM=true`**，否则会跳过登录认证。
- 其他可选变量：
  - `DATABASE_PATH`：默认 `~/.cloudcli/auth.db`。
  - `CLAUDE_CLI_PATH`：一般不用填，Windows 下会通过 `where.exe claude` 自动查找。
  - `JWT_SECRET`：不填时自动生成并保存在数据库中。

## 4. HTTPS 证书

证书目录建议放在 `C:\Users\<用户名>\.cloudcli\certs\`。以下命令都在该目录下的 PowerShell 中执行：

```powershell
$ossl = "C:\Program Files\Git\mingw64\bin\openssl.exe"
New-Item -ItemType Directory -Force "$HOME\.cloudcli\certs" | Out-Null
cd "$HOME\.cloudcli\certs"
```

### 4.1 CA：二选一

**方案 A：沿用原机的 CA（推荐）**

把原机 `C:\Users\Administrator\.cloudcli\certs\` 下的 `ca.crt` 和 `ca.key` 复制到新机同一目录。已经信任过这个 CA 的手机和电脑就不用再导入了。

**方案 B：新建 CA**

新 CA 有效期 10 年。

```powershell
& $ossl req -x509 -newkey rsa:3072 -sha256 -days 3650 -nodes `
  -keyout ca.key -out ca.crt -subj "/CN=CloudCLI Local CA" `
  -addext "basicConstraints=critical,CA:TRUE" `
  -addext "keyUsage=critical,keyCertSign,cRLSign"
```

### 4.2 为新 IP 签发服务器证书（两个方案都要做）

先新建 `server.ext`，把 IP 改成新机的：

```powershell
@"
basicConstraints=CA:FALSE
keyUsage=digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:<你的DDNS域名>,IP:<新机IP>,IP:127.0.0.1,DNS:localhost
"@ | Set-Content -Encoding ascii server.ext
```

**所有要用来访问的地址都必须列进 `subjectAltName`**，包括内网 IP 和公网 DDNS 域名。漏了域名的话，用域名访问会报 `ERR_CERT_COMMON_NAME_INVALID`；如果同时开了设备证书验证，浏览器还可能先弹 `ERR_BAD_SSL_CLIENT_AUTH_CERT`，看起来像客户端证书有问题，实际是服务器证书的 SAN 不匹配。判断方法：换成内网 IP 访问，如果正常就是 SAN 少了域名。

然后签发：

```powershell
& $ossl req -new -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj "/CN=<新机IP>"
& $ossl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial `
  -out server.crt -days 397 -sha256 -extfile server.ext
& $ossl verify -CAfile ca.crt server.crt   # 输出 server.crt: OK 即成功
```

- 有效期 397 天是浏览器接受的上限，到期前重新执行本节即可。
- 以后换 IP 或换域名，只需修改 `server.ext` 并重新签发。

#### 多台机器共用同一张服务器证书

**证书只绑定主机名，不绑定端口**，所以一张含 `DNS:awakelink.servegame.com` 的证书对该域名下的所有端口都有效（33001、33003 等都一样）。如果所有机器都通过同一个 DDNS 域名访问、只是端口不同，可以只签一张证书给全部机器共用。

在其中一台机器上签发一次：

```powershell
$ossl = "C:\Program Files\Git\mingw64\bin\openssl.exe"
cd "$HOME\.cloudcli\certs"
New-Item -ItemType Directory -Force -Path 共用证书 | Out-Null
cd 共用证书

@"
basicConstraints=CA:FALSE
keyUsage=digitalSignature,keyEncipherment
extendedKeyUsage=serverAuth
subjectAltName=DNS:<你的DDNS域名>,IP:127.0.0.1,DNS:localhost
"@ | Set-Content -Encoding ascii server.ext

& $ossl req -new -newkey rsa:2048 -nodes -keyout server.key -out server.csr `
  -subj "/CN=<你的DDNS域名>"
& $ossl x509 -req -in server.csr -CA ..\ca.crt -CAkey ..\ca.key -CAcreateserial `
  -out server.crt -days 397 -sha256 -extfile server.ext
& $ossl verify -CAfile ..\ca.crt server.crt
```

然后把 `server.crt` 和 `server.key` 复制到每台机器，各自 `.env` 里的 `SSL_KEY_FILE` / `SSL_CERT_FILE` 指向它们，重启服务即可。

需要权衡的两点：

- **私钥会存在多台机器上**，任何一台被入侵都等于所有机器的服务器私钥泄露，届时必须重签并更换全部机器。安全性低于各机器独立签发。
- **只有域名可用**。SAN 里的 IP 只能写一台机器的，所以在局域网内用 `https://<内网IP>:端口` 直连非该机器时会报 `ERR_CERT_COMMON_NAME_INVALID`（Node 下是 `ERR_TLS_CERT_ALTNAME_INVALID`）。如果主要用某一台的内网 IP，可以把那台的 IP 也加进 SAN。

想避免共用私钥，就按前面的方式各机器单独签发一张，`server.ext` 里同时写上域名和该机器的内网 IP。设备证书（`.p12`）与此无关，一份通吃所有机器和端口。

### 4.3 在访问端信任 CA（只导入 `ca.crt`，不要给出 `ca.key`）

- **Windows**：`certutil -addstore -user Root ca.crt`，或者双击 `ca.crt` → 安装证书 → 受信任的根证书颁发机构。之后重启浏览器。
- **iOS**：用 AirDrop 或邮件发送 `ca.crt` 并安装描述文件，然后在「设置 → 通用 → 关于本机 → 证书信任设置」中打开完全信任。
- **Android**：「设置 → 安全 → 加密与凭据 → 安装证书 → CA 证书」。
- **macOS**：导入钥匙串，然后把该证书设为「始终信任」。

### 4.4 设备证书验证（双向 TLS，可选但推荐）

开启后，没有安装设备证书的客户端在 TLS 握手阶段就被拒绝，连登录页都打不开，等于在密码和 TOTP 之前多加一道门。

证书文件放在项目下的 `client-certs\`（该目录已在 `.gitignore` 中，私钥不会进仓库）。

**签发设备证书**（复用 4.1 的 CA）：

```powershell
$ossl = "C:\Program Files\Git\mingw64\bin\openssl.exe"
$ca = "C:\Users\Administrator\.cloudcli\certs"
New-Item -ItemType Directory -Force -Path client-certs | Out-Null
Copy-Item "$ca\ca.crt" client-certs\cloudcli-ca.crt -Force

@"
basicConstraints=CA:FALSE
keyUsage=digitalSignature,keyEncipherment
extendedKeyUsage=clientAuth
"@ | Set-Content -Encoding ascii client-certs\client.ext

& $ossl req -new -newkey rsa:2048 -nodes -keyout client-certs\client.key `
  -out client-certs\client.csr -subj "/CN=cloudcli-device"
& $ossl x509 -req -in client-certs\client.csr -CA "$ca\ca.crt" -CAkey "$ca\ca.key" `
  -CAcreateserial -out client-certs\client.crt -days 3650 -sha256 `
  -extfile client-certs\client.ext
& $ossl pkcs12 -export -inkey client-certs\client.key -in client-certs\client.crt `
  -certfile client-certs\cloudcli-ca.crt -out client-certs\cloudcli-device.p12 `
  -name "CloudCLI Device" -passout pass:<设置一个导入密码>

# 把设备端要用的两个文件单独放一份，方便整个目录传给手机
New-Item -ItemType Directory -Force -Path client-certs\给手机用 | Out-Null
Copy-Item client-certs\cloudcli-ca.crt, client-certs\cloudcli-device.p12 client-certs\给手机用\ -Force
```

**启用**：在 `.env` 中加一行，指向用于校验客户端证书的 CA，然后重启服务。

```ini
SSL_CLIENT_CA_FILE=D:\CommonProject\claudecodeui\client-certs\cloudcli-ca.crt
```

不配这一行就是原来的单向 HTTPS 行为，不影响现有部署。启动日志出现 `Client certificate required` 即表示已生效。

**在设备上安装**：要装的是两个文件，作用不同，区域也不同，装错区域是最常见的失败原因。

| 文件 | 作用 | 装到哪 |
|---|---|---|
| `cloudcli-ca.crt` | 信任服务器证书，消除"不安全"警告 | 受信任的**根证书** |
| `cloudcli-device.p12` | 设备通行证，没有它连不上 | **个人 / 用户**证书 |

`client-certs\给手机用\` 目录里只放了这两个文件，直接整个传到手机即可。

- **Windows**：双击 `client-certs\安装证书.bat`，两张证书一起装好。中途会弹一次安全警告，点"是"。装完完全关闭浏览器再重开。
- **iOS / iPadOS**：AirDrop 或邮件发送两个文件 → 分别点开 → 设置 → 通用 → VPN 与设备管理 → 已下载的描述文件 → 安装（装 `.p12` 时输入导入密码）。**然后必须再做一步**：设置 → 通用 → 关于本机 → 拉到最底 → 证书信任设置 → 打开 `CloudCLI Local CA` 的开关，否则 CA 不生效。
- **Android**：设置里搜"证书"进入「加密与凭据 → 安装证书」，两个文件走**不同入口**：`cloudcli-ca.crt` 选「CA 证书」，`cloudcli-device.p12` 选「VPN 和应用用户证书」。注意 **Android 版 Chrome 不支持客户端证书**，装了也会连接失败，请改用 Firefox。
- **macOS**：双击两个文件导入钥匙串，然后把 `CloudCLI Local CA` 设为「始终信任」。

装完访问站点，按现象判断：地址栏是锁头且页面正常 = 两张都对；连接被拒绝或 `ERR_BAD_SSL_CLIENT_AUTH_CERT` = 设备证书没装或装错区域；能打开但提示"不安全" = 设备证书对了，CA 没装（iOS 上多半是忘了开信任开关）。

> `client.key` 和 `.p12` 等同于门禁钥匙，只在受信任的设备上安装，不要通过公开渠道传输，用微信之类传完记得删掉聊天记录里的文件。想吊销某台设备，重新签一套新证书并替换 CA 即可（当前实现没有 CRL）。

**验证**：

```powershell
node -e "const https=require('https'),fs=require('fs');https.request({host:'192.168.1.202',port:33001,path:'/api/auth/status',rejectUnauthorized:false},r=>console.log('no cert:',r.statusCode)).on('error',e=>console.log('no cert:',e.code)).end()"
```
期望输出 `no cert: ERR_SSL_TLSV13_ALERT_CERTIFICATE_REQUIRED`，即无证书确实被拒。

### 4.5 一份设备证书访问多台机器

客户端证书和服务器证书的校验方向是相反的，这点容易混淆：

- **服务器证书**（`server.crt`）必须绑定 IP 或域名，所以每台机器都要按 4.2 单独签发。
- **客户端证书**（`client.crt`）里不含任何主机名，只有 `CN` 和 `clientAuth` 用途。服务器只校验它是否由自己信任的 CA 签发，与访问哪台机器、哪个 IP、哪个端口无关。

所以**多台机器只要 `SSL_CLIENT_CA_FILE` 指向同一个 CA，一份 `cloudcli-device.p12` 就能访问全部机器**，不需要为每台机器各签一份。

做法：把 `cloudcli-ca.crt` 复制到每台机器（只复制 CA 证书，`ca.key` 留在签发机器上），各自 `.env` 里的 `SSL_CLIENT_CA_FILE` 指向它即可。按 4.1 的方案 A 共用 CA 时这一步本来就已满足。若某台机器当初是自建的 CA，需要换成统一的 CA 并重新签发服务器证书，客户端证书不用动。

同一份 `.p12` 也可以同时装在手机、平板和电脑上，服务器不做设备去重。代价是无法单独吊销某台设备——当前实现没有 CRL，想踢掉一台就只能重签整套并替换 CA，所有设备都要重新导入。有这个需求时，给每台设备单独签一张证书（`CN` 用 `cloudcli-phone`、`cloudcli-laptop` 等区分），服务器侧配置不用改，因为它们仍由同一个 CA 签发。

## 5. TOTP 两步验证

### 5.1 生成密钥

生成 32 位 Base32 密钥，对应 160 bit：

```powershell
node -e "const c=require('crypto'),a='ABCDEFGHIJKLMNOPQRSTUVWXYZ234567';let b='';for(const x of c.randomBytes(20))b+=x.toString(2).padStart(8,'0');let s='';for(let i=0;i<b.length;i+=5)s+=a[parseInt(b.slice(i,i+5),2)];console.log(s)"
```

把输出填进 `.env` 的 `TOTP_SECRET=`。

- 想和原机共用验证器里的同一个条目，也可以直接沿用原机 `.env` 中的值。
- 分开使用更安全。

### 5.2 添加到验证器

在 Google Authenticator、Microsoft Authenticator 等 App 中选择「输入设置密钥」：

- 账户名随意
- 密钥填上面生成的字符串
- 类型选「基于时间」（6 位、30 秒）

### 5.3 注意

- 服务器和手机的时间必须准确，允许误差约 ±30 秒。
- 同一个验证码只能使用一次，有防重放保护。
- 修改或删除 `TOTP_SECRET` 后要重启服务才会生效。

## 6. Claude Code 认证

CloudCLI 调用本机的 Claude Code，所以新机需要先把 Claude Code 配好，两种方式任选：

- **官方账号**：运行 `claude`，然后在里面执行 `/login`。
- **第三方 / 中转 API**：编辑 `C:\Users\<用户名>\.claude\settings.json`：

  ```json
  {
    "env": {
      "ANTHROPIC_BASE_URL": "https://你的中转地址",
      "ANTHROPIC_AUTH_TOKEN": "你的 Token"
    }
  }
  ```

  如果使用 CC Switch，切换供应商时它会覆盖这个文件，属于正常现象。

先在命令行运行 `claude` 确认能正常对话，再启动 CloudCLI。

## 7. 启动与首次使用

```powershell
cd D:\CommonProject\claudecodeui
npm.cmd run server
```

- 浏览器访问 `https://<新机IP>:33001`。
- 如果开了设备证书验证（第 4.4 节），访问前必须先在该设备上导入 `cloudcli-device.p12`，否则浏览器直接报连接失败，看不到登录页。
- **第一次访问会进入注册页面**，创建唯一的管理员账号，之后就不能再注册了。
- 登录时需要输入用户名、密码和 6 位验证码（如果开启了 TOTP）。
- 同一 IP 连续失败 5 次会被锁定 15 分钟（返回 HTTP 429）。锁定记录保存在内存中，重启服务即可解除。
- 登录令牌有效期 7 天，期间会自动续期。

### 防火墙

如果 Windows 防火墙是开启的，需要放行端口，并且只允许局域网访问。用管理员 PowerShell 执行：

```powershell
New-NetFirewallRule -DisplayName "CloudCLI 33001" -Direction Inbound -Protocol TCP `
  -LocalPort 33001 -Action Allow -RemoteAddress 192.168.1.0/24
```

### 开机自启（任务计划程序 + S4U）

用 Windows 自带的任务计划程序配合 S4U（Schedule As User）登录类型，可以做到开机即启动、不需要用户登录、不需要存储密码，同时仍以当前用户身份运行（因此能读到 `~\.cloudcli` 和 `~\.claude`），并在进程崩溃后自动重启。

**为什么不用 NSSM 或真正的 Windows 服务**：S4U 已经同时满足"不登录就启动""用户身份运行""不存密码"这三点，而任务计划程序是系统自带的，配置也更透明。需要服务依赖、详细日志或图形化配置时再考虑 NSSM。

#### 1. 启动脚本

S4U 任务在用户 profile 加载之前就运行，此时 `USERPROFILE` 会回落到 `C:\Users\Default`，导致 `~/.cloudcli/auth.db` 和 `~/.claude` 全部指错位置。所以不要让任务直接执行 `node.exe`，而是通过项目根目录下的 `start-cloudcli.cmd` 把这些变量钉死：

```bat
@echo off
set "USERPROFILE=C:\Users\<用户名>"
set "HOMEDRIVE=C:"
set "HOMEPATH=\Users\<用户名>"
set "APPDATA=C:\Users\<用户名>\AppData\Roaming"
set "LOCALAPPDATA=C:\Users\<用户名>\AppData\Local"
set "PATH=C:\Users\<用户名>\.local\bin;C:\Users\<用户名>\AppData\Roaming\npm;C:\Program Files\nodejs;%PATH%"
cd /d "%~dp0"
"C:\Program Files\nodejs\node.exe" dist-server\server\index.js
```

#### 2. 注册任务

用**管理员** PowerShell 执行：

```powershell
cd D:\CommonProject\claudecodeui
$action = New-ScheduledTaskAction -Execute "D:\CommonProject\claudecodeui\start-cloudcli.cmd" -WorkingDirectory "D:\CommonProject\claudecodeui"
$trigger = New-ScheduledTaskTrigger -AtStartup
$principal = New-ScheduledTaskPrincipal -UserId "$env:USERNAME" -LogonType S4U -RunLevel Highest
$settings = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries -DontStopIfGoingOnBatteries `
  -ExecutionTimeLimit (New-TimeSpan -Hours 0) -RestartCount 3 -RestartInterval (New-TimeSpan -Minutes 1) `
  -StartWhenAvailable
Register-ScheduledTask -TaskName "CloudCLI" -Action $action -Trigger $trigger `
  -Principal $principal -Settings $settings -Description "CloudCLI Web UI"
```

关键设置的含义：

| 设置 | 值 | 作用 |
|---|---|---|
| 触发器 | AtStartup | 开机就启动，不用等用户登录 |
| 登录类型 | S4U | 不存密码，且登录与否都能运行 |
| 执行时限 | 0 | 不会在 72 小时后被自动杀掉 |
| 失败重启 | 3 次 / 间隔 1 分钟 | 进程崩溃后自动拉起 |

#### 3. 验证

```powershell
Get-ScheduledTask -TaskName CloudCLI | Select-Object TaskName, State,
  @{N='Trigger';E={($_.Triggers | ForEach-Object { $_.CimClass.CimClassName }) -join ', '}},
  @{N='LogonType';E={$_.Principal.LogonType}}
```

期望 `State=Ready`、`Trigger=MSFT_TaskBootTrigger`、`LogonType=S4U`。然后：

```powershell
Start-ScheduledTask -TaskName CloudCLI
Start-Sleep -Seconds 10
Get-NetTCPConnection -LocalPort 33001 -State Listen
```

#### 4. 重启服务

改了后端代码并重新构建后必须重启任务，否则跑的还是旧的 `dist-server/`。**不要用 `Stop-Process -Name node`**，那会连带杀掉其他 Node 程序：

```powershell
Stop-ScheduledTask CloudCLI
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -match 'dist-server' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
Start-ScheduledTask CloudCLI
```

也可以直接双击 `tools\更新并重启.bat`，它会依次执行 `git pull`、`npm install`、`npm run build` 和上面的重启流程。

删除任务：`Unregister-ScheduledTask -TaskName CloudCLI -Confirm:$false`

#### 5. 任务相关排查

- **任务没起来**：查事件日志
  ```powershell
  Get-WinEvent -LogName Microsoft-Windows-TaskScheduler/Operational -MaxEvents 50 |
    Where-Object { $_.Message -like '*CloudCLI*' }
  ```
- **登录后发现要重新注册账号，或读不到 Claude 配置**：说明 `USERPROFILE` 指错了，检查 `start-cloudcli.cmd` 里的路径。
- **任务计划程序不会加载 PowerShell Profile**，`.env` 必须放在项目根目录。
- **端口被占用**：`Get-NetTCPConnection -LocalPort 33001`，改 `.env` 里的 `SERVER_PORT` 后重启任务。

## 10. 已知问题

- **Browser Use 功能**：`server/modules/browser-use/browser-use.service.ts` 固定访问 `http://127.0.0.1:端口`。当 `HOST` 设为局域网 IP 或开启 HTTPS 时，该功能不可用；不影响其他功能。
- **开启设备证书后浏览器直接报连接失败**：说明该设备没装或没选中客户端证书。错误信息一般是 `ERR_BAD_SSL_CLIENT_AUTH_CERT` 或 `ERR_SSL_PROTOCOL_ERROR`，不会提示“需要证书”。临时排查时可以注掉 `.env` 里的 `SSL_CLIENT_CA_FILE` 重启。
- **换用域名访问时报 `ERR_BAD_SSL_CLIENT_AUTH_CERT`，但内网 IP 正常**：这不是客户端证书的问题，而是服务器证书的 `subjectAltName` 里没有该域名。按 4.2 把域名加进 `server.ext` 重新签发即可。
- **Windows 证书链显示 `RevocationStatusUnknown`**：自建 CA 没有 CRL 分发点，属正常现象，不影响 Chrome / Edge 使用客户端证书。
- **命令行工具报 TLS 握手失败**：Windows 自带的 `curl.exe` 用 schannel，不支持从文件加载客户端证书（会提示 `disabled automatic use of client certificate`）。改用 Node 脚本或 Git 自带的 curl。
- 插件以完整权限运行，只安装信任的插件。

## 11. 安全要点

- `ca.key`、`server.key`、`client-certs\` 下的客户端私钥和 `.p12`、`TOTP_SECRET`、`~/.claude/settings.json` 中的 Token 都不要外传，也不要提交到 Git。
- `ca.key` 泄露意味着别人可以伪造证书，这时应按方案 B 重新建 CA，并在所有设备上替换信任。
- 多台机器共用同一张服务器证书时，`server.key` 存在于每台机器上，任何一台被入侵都要重签并更换全部机器。
- 不要把端口直接映射到公网。需要远程访问时，请使用 VPN 或 Tailscale 等组网工具。
